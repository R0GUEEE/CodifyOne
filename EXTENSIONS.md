# Extensions

CodifyOne runs **real VS Code extensions** — the same `.vsix` packages you would
install into desktop VS Code — inside its editor.

This document explains what is supported, how the pieces fit together, and where
the limits are.

## What works

| Capability | Status |
| --- | --- |
| Install from Open VSX (search, download, unpack) | ✅ |
| Install from a `.vsix` file on device | ✅ |
| Extension host (activate/deactivate, command registration) | ✅ |
| `vscode` API: commands, window, workspace (documents/configuration), languages (completion, hover, definition, diagnostics, formatting, code actions, document symbols), env, extensions | ✅ |
| Manifest contributions: commands, languages, grammars, snippets, keybindings, configuration, themes | ✅ (handled by the real VS Code services) |
| Enable / disable / uninstall | ✅ |
| Node-only extensions (`main` without `browser`) | ❌ rejected at runtime |
| `workspace.fs` access to files outside the open editor models | ⚠️ virtual workspace only (see *Limits*) |

## Why web extensions?

The editor web app is built on
[`@codingame/monaco-vscode-api`](https://github.com/CodinGame/monaco-vscode-api),
which embeds the VS Code **extension host** and a complete implementation of the
`vscode` extension API. Extensions therefore run in a web context, exactly like
they do on vscode.dev.

That means a package must provide a `browser` entry point in its `package.json`:

```json
{
  "main": "./out/extension.js",       // node — ignored on iOS
  "browser": "./out/extension-web.js" // used by CodifyOne
}
```

Packages without a `browser` entry are still installable but CodifyOne reports
them as unsupported instead of failing silently.

## Architecture

```
┌──────────────────────────────────────────────────────────────────┐
│ CodifyOne.app                                                    │
│                                                                  │
│  ExtensionInstaller ──(VSIX unzip)──▶ Application Support/       │
│  (ZIPFoundation)                      Extensions/<pub>.<name>/   │
│                                              │                   │
│  ExtensionRuntime ◀── scans ─────────────────┘                   │
│    writes index.json  (manifest + file list + base URL)          │
│                                              │                   │
│  EditorService (GCDWebServer, 127.0.0.1:20234)                   │
│    /            → monaco-textmate.bundle                         │
│    /ext/…       → Application Support/Extensions                 │
│                                              │                   │
│  WKWebView ──────────────────────────────────┘                   │
│    window.codeExtensions.load() → /ext/index.json                │
│    registerExtension(manifest, LocalProcess)                     │
│    registerFileUrl(file, http://…/ext/<id>/<file>)               │
│    ↓                                                             │
│  VS Code extension host (in-page, real `vscode` API)             │
│    activate() → commands / language features → Monaco            │
└──────────────────────────────────────────────────────────────────┘
```

Key points:

* **The extension host is real.** Nothing here re-implements `vscode.*`; the
  extension gets the API object generated by the VS Code sources that ship in
  the editor bundle.
* **Extensions run in the local (in-page) extension host.** That host kind is
  the only one where `registerFileUrl()` mappings are visible to the module
  loader, which is what allows extension code to be served straight out of the
  app sandbox over loopback HTTP.
* **Native owns installation.** Downloading, unzipping, enablement and removal
  happen in Swift; the web layer only reads the index and registers packages.
* **Same-origin.** The editor and extension files are served from the same
  `http://127.0.0.1:20234` origin, so module loading needs no CORS relaxation.

### Native API surface

`ExtensionRuntime` (Swift) and `window.codeExtensions` (JS) are the contract:

| Swift | JS |
| --- | --- |
| `ExtensionRuntime.shared.reload()` | `codeExtensions.load()` |
| `MonacoImplementation.reloadWebExtensions()` | `codeExtensions.sync()` |
| `MonacoImplementation.executeExtensionCommand(_:)` | `codeExtensions.executeCommand(id, …)` |
| `ExtensionRuntime.shared.packages` | `codeExtensions.list()` / `listCommands()` |

Events flow back to native through the existing WKWebView message bridge as
`Extension Ready`, `Extension Error` and `Extension Unloaded`.

## Installing

* **From Open VSX** — the Extensions sidebar queries `open-vsx.org/vscode/gallery`
  (the same protocol VS Code uses; Microsoft's marketplace terms forbid
  third-party clients, Open VSX is the open registry).
* **From a file** — any `.vsix` can be installed from the document picker.

After installation the package is indexed and pushed into the running extension
host, so contributed commands and language features are live without a restart.

## Limits

* **Web extensions only.** Node APIs (`fs`, `child_process`, native modules) are
  not available. Anything that ships a `browser` bundle works.
* **Filesystem.** Extensions see the editor's open documents (content, version,
  selection, edits) through the standard text-document API. The underlying file
  service is still the web workbench's virtual workspace, so an extension that
  walks the filesystem (`workspace.findFiles`, `workspace.fs.readFile`) will not
  see the iPad's real directory tree yet. Bridging `file://` to the app sandbox
  is the next milestone.
* **No marketplace UI inside the editor.** Browsing/installing is driven by the
  native Extensions sidebar.
* **Performance.** Extensions execute on the editor's JS thread. This is the same
  model as vscode.dev; heavy extensions will compete with the editor.

## Building

The editor bundle is built from
[`R0GUEEE/codeapp-monaco`](https://github.com/R0GUEEE/codeapp-monaco) (GitHub
Actions: *Bundle CI*, which also runs a headless smoke test that installs a
fixture extension, activates it and executes a contributed command).

The iOS app's *Build Unsigned IPA* workflow builds that bundle, drops it into
`Resources/`, downloads the missing Apple frameworks and produces an unsigned
IPA artifact.

## Adding a test extension

`test/fixture` in the editor repo is the reference package: it contributes
commands, declares a `browser` entry point and can be installed into the app by
zipping it as a VSIX:

```sh
cd test/fixture
zip -r ../codify-test-extension.vsix .
```
